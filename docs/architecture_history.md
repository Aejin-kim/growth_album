# Growth Album Architecture History (아키텍처 변경 이력)

본 문서는 Growth Album 웹 서비스가 발전하면서 핵심 아키텍처와 로직이 어떻게 변화해왔는지 그 역사와 배경(Why)을 기록하는 문서입니다.

---

## 1. 초기 구조 (V1): 로컬 JSON과 강제 다운로드 아키텍처

**시점:** 프로젝트 초기 ~ 2026년 4월
**주요 스택:** React + Node.js Proxy + Local JSON (`photos.json`)

### 1-1. 당시의 주요 요구사항
- 구글 포토 API (Picker API 등)에서 제공받는 미디어 링크(`baseUrl`)는 보안상 생성 후 약 60분이 지나면 만료되는 치명적인 문제가 있었습니다.
- 이를 해결하기 위해 사용자가 구글 포토에서 이미지를 선택하면, 클라이언트가 백엔드(Node.js 프록시)로 요청을 전송하고 백엔드가 실시간으로 해당 사진 데이터 원본 파일(Buffer)을 다운로드하여 `data/images` 로컬 디렉토리에 영구 보존하는 방식을 채택했습니다.

### 1-2. 발생한 문제점 및 한계 (설계적 오판)
- **불필요한 리소스 및 서버 부하:** 사용자는 그저 앨범을 관리/분류하기 위해 사진을 불러왔음에도 불구하고, 선택 즉시 무조건 사진 원본을 로컬 서버로 다운로드하게 만들었습니다. 만약 수백 장을 한 번에 구성하려 할 경우 디스크 용량, 네트워크 트래픽, 대기 시간 등에서 극심한 병목 현상이 발생합니다.
- **배포의 한계:** 최종 배포 대상(Firebase, Supabase, Cloudflare 등 클라우드 플랫폼) 환경은 로컬 파일시스템에 직접 영구적으로 쓰기 작업(Write)을 하는 것이 권장되지 않거나 불가능했습니다. (Local JSON 파일과 Local Directory 의존도가 너무 큼)

---

## 2. 구조 개편 (V2): 2단계 지연 로딩(Lazy Loading) 및 Supabase 마이그레이션

**시점:** 2026년 4월 말 (현재 진행)
**주요 방향:** 로컬 의존성 탈피, 트래픽 최적화, RDBMS(Supabase) 도입

### 2-1. 개선 목표 및 변경 사항

1. **2단계 허가(지연 로딩) 시스템 도입:**
   - **(단계 1) 등록 및 관리:** 사용자가 구글 포토에서 추억 사진들을 선택하면 **오직 메타데이터(링크, ID 등)만 DB에 저장**합니다. 화면에는 "인증시 보여짐" 이라는 임시 이미지를 출력하여 앨범 정리를 매우 빠르고 쾌적하게 돕습니다.
   - **(단계 2) 최종 네트워크 동기화:** 앨범 정리가 끝나고 최종 완성(최종 권한 승인)을 누르면, 그때 구글 포토 망을 경유해 실제 사진 데이터들을 안전한 형태로 끌어옵니다.

2. **Supabase로의 DB 이전:**
   - 연도별(Year) > 테마(Theme) > 사진(Photo)이라는 데이터의 계층적-관계형 구조를 효과적으로 관리하기 위해 **PostgreSQL 기반의 Supabase**를 채택했습니다.
   - 이를 통해 향후 사용자 인증 분리, 퍼블릭/프라이빗 링크 공유 기능의 도입 시점에서도 훨씬 단단한 기반을 가지게 되었습니다.
   - 기존의 `data/photos.json` 및 `data/images` 파일시스템 맹신 구조를 전면 폐기합니다.
